## Artifact retry kept the old upstream model

- **Reported symptom**: after changing the OpenRouter model to `minimax/minimax-m2.7:free`, clicking retry on a bookshelf artifact task still requested `z-ai/glm-5.2:free` and returned an upstream rate-limit error.
- **Root cause**: the artifact job persisted `model_id` when it was created. The bookshelf retry endpoint only changed `status` back to `queued`; execution correctly called `make_client(model_id=job.model_id, ...)`, so it faithfully reused the stale model recorded on the failed job.
- **Fix**: retry now snapshots the current application `model` and `fake` settings into the same durable job before queueing it. The preparation task scope and profile remain unchanged.
- **Step isolation**: the model identity and fake/real mode are included in each resumable step input fingerprint and provenance refs. A retry with the same model reuses successful steps; switching models starts fresh step keys and prevents a final job from silently mixing responses from two models.
- **Regression (historical)**: the former supplemental workflow test switched from a legacy model to `minimax/minimax-m2.7:free` before retry; that test was removed with the path.

## Preparation retry kept the old upstream model (2026-08-30)

- **Reported symptom**: after changing the configured OpenRouter model, retrying a failed preparation task from the bookshelf still sent requests to the model captured when the task was first created.
- **Root cause**: the preparation retry endpoint only changed window status; `start_prep_job` and the shadow-task idempotency key continued to use the stale job model.
- **Fix**: the retry endpoint now snapshots the current `model` and `fake` settings into the durable preparation job. The idempotency key includes a short hash of that snapshot, so a model switch creates a new shadow task while retaining the old attempt history.
- **Regression**: `scripts/test_prep_retry_model.py` verifies the model snapshot, isolated shadow task, and distinct idempotency keys.

## Deleted artifacts resumed an old generation task (2026-08-31)

- **Reported symptom**: after deleting an old board and reviewing a fresh p1-20 task, the shelf appeared to return the old artifacts; after deleting again, the new board would not start cleanly.

## Importing the backend initialised the real database (2026-09-13)

- **Reported symptom**: running `scripts/test_*.py` modified the real
  `data/app.db` — its content hash and mtime moved while its byte size stayed
  identical — even though every storage-touching test patches `storage.DB_PATH`
  to a temporary file.
- **Root cause**: `backend/app/main.py` called `storage.init_db()` at module
  scope. Merely importing the ASGI app therefore executed
  `CREATE TABLE IF NOT EXISTS` against whatever `storage.DB_PATH` held at import
  time. Every ASGI test imports the app before its own patch takes effect, so the
  real database was written. The statement is idempotent DDL, which is why the
  file size did not change.
- **Fix**: `storage.init_db()` now runs inside the existing `lifespan` hook,
  which already owns start-up persistence maintenance, instead of at import time.
- **Verification**: importing `backend.app.main` leaves `data/app.db` untouched,
  and the full `scripts/test_*.py` suite no longer modifies the real database.
- **Second hazard fixed in the same pass**: eight scripts (`test_chunks`,
  `test_cancel`, `test_e2e`, `test_incremental`, `test_joke`, `test_light`,
  `test_processed`, `test_staged`) called a real service on `127.0.0.1:8000` and
  created real rows through it. `POST /api/campaigns` inserted campaign rows
  named 取消测试, 增量验证, processed验证, 分阶段测试, and 无光的灯塔（实测） into
  the developer database, and rows with the same names recur from 2026-09-01, so
  this predates the import-time defect rather than following from it. Every
  guarded script now calls `require_live_tests` from `scripts/_live_guard.py` and
  exits 0 with a SKIP line unless `TRPG_LIVE_TESTS=1` is set. The guard sits
  before the first non-import statement, so it runs before any HTTP request.
- **Cleanup**: the five campaign rows created during this investigation were
  deleted; the pre-2026-09-13 rows were left untouched. Row counts for all
  nineteen tables then matched the pre-run backup exactly.

## A hidden fact-count ceiling refused cards the budget had approved (2026-09-13)

- **Reported symptom**: once the cross-chapter merge guard measured a card's fact
  closure against the materialize budget, `test_fantasy_long_artifact_workflow`
  failed with `产物 FakeLLM environment 1 的事实闭包超过允许上限` on card 1 of 128.
- **Root cause**: three limits disagreed. `_validate_global_plan` and the merge
  guard both measure the character/token budget, but the closure guard inside
  `_validate_and_build` compared against a literal `100` written in the loop body.
  A merge the budget admitted was therefore refused later for its fact count.
- **Fix**: that guard now measures the same character/token budget and treats the
  fact count only as a structural ceiling, so a card that passed planning can no
  longer be refused during materialization for its count.
- **Ceiling**: `MAX_MERGED_FACT_IDS` is now 600 instead of 100. Measured, the
  leanest serialized fact payload is about 300 characters and 80 tokens, so the
  character budget binds at roughly 240 facts and the ceiling never binds first.
  The merge guard falls back to this count only when it is given no fact table.
- **Regression**: `scripts/test_merge_budget.py` covers the budget-driven merge,
  and `scripts/test_artifact_shape_normalization.py` now exercises an under-budget
  merge and an over-budget split of the same cross-chapter pair.
- **Real data**: replaying the 175 planned cards of the verified 8-chapter run
  yields 172 survivors under both the old count rule and the new budget rule, so
  the change closes the failure mode without altering current output.

## A per-fact disposition list made large chapters unplannable (2026-09-13)

- **Reported symptom**: a real six-chapter build failed with `全局规划失败：规划请求过大：
  固定章节上下文与事实编号至少占 121,982 字符，超过 120,000 字符预算；未调用索引汇总或
  截断事实。` Two chapter scopes had planned; the third refused before any index prose
  was even considered.
- **Diagnosis**: reproduced from the workspace bundle, matching the reported 121,982
  exactly. Four of the six scopes exceeded the budget with no prose at all, and
  `REVIEWED_STRUCTURE_JSON` was 74% of the request. Inside it, `fact_dispositions` was
  90% of the structure block, at about 110 characters per fact: each fact was sent as
  its own record carrying a `fact_id`, a `kind` that is always `chapter` for this
  profile, a `chapter_ids` list that always contains the scope chapter, and its
  `thread_ids`. Filtering the redundant records saved 94 characters, so the cost was
  the shape rather than duplicated entries.
- **Fix**: a chapter scope now sends the same mapping transposed — one record per thread
  and per other chapter, each carrying a `fact_ids` list — plus `chapter_fact_ids` naming
  the facts the request must account for. No information is dropped.
- **Constraint found**: `PlanningTransport` rewrites identifiers only under known field
  names, so a map keyed by a thread id left every fact id at its full 40-character
  length and cost more than the records it replaced. `chapter_fact_ids` joins that set.
- **Result on the reported workspace**: the failing chapter fell from 121,982 to 63,856
  characters and the largest from 144,457 to 74,555; all six scopes now fit with 38%
  headroom.
- **Contract**: `GLOBAL_PLAN_PROMPT_VERSION` is now `prep-artifact-global-plan-v14`, and
  the fixture planner in `backend/app/llm.py` reads `chapter_fact_ids` instead of the
  removed per-chapter `fact_dispositions`.
- **Diagnosability**: the fixture assertion that caught the shape mismatch carried no
  message, so the wrapped error read `全局规划失败：` with nothing after it. It now
  reports the set difference, which is what located the unencoded identifiers.
