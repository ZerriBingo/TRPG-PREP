# 2026-08-26 连续复核、产物审批与运行场景维护记录

## 触发反馈

GM 在真实复核中指出：

- 接受一条候选后界面直接切到“已接受”，继续复核下一条需要额外切换和查找。
- 批量状态与“应用至已选候选”含义不清，同时又有一个突出的“提升已选为原文事实”按钮，审核和入库阶段混在一起。
- 全部候选送入书架后没有明确下一步；“生成场景包”既不可用，名称也不能覆盖 NPC、威胁、环境、时钟等多种备团产物。

## 连续复核决定

候选复核是队列工作，不是详情页跳转：

1. 单条接受或拒绝后保持“待复核”筛选。
2. 自动选择当前任务中的下一条待复核候选。
3. 当前来源页没有候选时继续任务内其他来源页，不要求 GM 手动清空页码筛选。
4. 只有整个待复核队列清空后才切到“已接受”，并提示把已接受候选送入书架。

批量区明确拆为两个阶段：

- **复核所选**：只改变候选的接受/拒绝/待复核状态，不写入书架。
- **送入书架**：只处理已经接受且尚未提升的候选，并明确选择“原文事实”或“可验证推断”。

## 产物与运行场景闭环

书架下一步固定为：

`已提升事实 -> 生成备团产物草案 -> 编辑/批准产物 -> 组装运行场景 -> 开始运行`

边界如下：

- 真实模型生成只能由 GM 在书架显式点击触发。
- 模型只读取已提升事实和当前目标板块契约，不读取未提升候选。
- 每张产物保存 `fact_ids`、字段级来源、模型与提示版本、生成时间和 `open_questions`。
- 模型输出永远是草案，不会自动批准。
- 只有 `approved` 产物能进入运行场景。
- 运行场景继承任务已经确定的 PDF、跨页范围、目标板块和时长，不再要求重复输入。
- 已被运行场景引用的产物不能退回修改或删除，避免已保存计划失效。

用户可见名称统一为“备团产物”“运行场景”和“组装运行场景”。“场景包”保留在历史文档中，不再作为当前按钮名称。

## 批量产物复核

“选择当前列表”允许混合选择已批准和待批准卡片。批量按钮只统计并处理自身可执行的子集：

- “批准所选”处理未批准草案；
- “退回修改”处理已批准且尚未被运行场景引用的产物；
- 不兼容状态不会让另一个可执行动作整体失效；
- 已引用产物的单条退回和删除按钮也会锁定并说明原因。

## 正式数据边界

本轮没有对正式“无光的灯塔 · p1-20”工作区触发 LLM、批准卡片或创建运行场景。正式数据在切换服务前应保持：

- 46 条书架事实；
- 0 项备团产物；
- 0 个运行场景。

所有生成、批准和组装验收均使用隔离的 `output/qa-r3.db` 与 FakeLLM。

## 实现与验证

主要实现：

- `backend/app/artifacts.py`：板块产物提示、严格 JSON 解析、字段来源与待确认问题归一化。
- `backend/app/main.py`：产物草案、批量审批和删除接口。
- `backend/domain/models.py`、`backend/domain/service.py`：产物 provenance、审批状态和运行场景消费约束。
- `frontend/workbench.html/js/css`：连续复核、分阶段批量操作、产物复核页、书架阶段摘要和运行场景入口。
- `scripts/test_artifact_workflow.py`：隔离生成、审批、场景解锁及引用锁定回归。

隔离 QA 结果：

- 接受一条后待复核计数从 46 变为 45，仍停留待复核并自动选中下一条。
- 46 条书架事实生成场景、NPC、威胁和推进钟 4 类 FakeLLM 草案。
- 4 张草案批量批准后，“组装运行场景”立即解锁。
- 组装继承 PDF、p1-20、现实恐怖和 120 分钟，保存为包含 5 个节拍的待开始草案。
- 390 x 844 与桌面宽度均无页面级横向溢出；卡片标题和操作区不再互相挤压。
