# R4 交接：备团方法与实际运行规则分离

状态：R4 已独立签收并同步两工作区，保持未提交，见 R4_IMPLEMENTATION_REVIEW.md。以下保留已完成切片的范围与验收依据；下一轮见 R6_IMPLEMENTATION_HANDOFF.md。

## 已确认的产品边界

现实恐怖、奇幻冒险是信息组织与备团需求。Cthulhu Dark、匕首心提供设计方法参考，产物也应服务按 COC、DND 等原规则运行的游戏。不要让参考规则替 GM 决定检定、失败后果或战斗机制。

保留有用的地点、人物诉求、社会阻力、环境功能、对手意图、非战斗解法、压力及后果。时钟、硬选择、危险前兆等叙事方法本身不构成规则越界；应检查具体措辞是否把可选方法写成强制执行的机制。不能为了中性化删掉可运行信息。

原规则的数值、能力、条件与规则文本可以保留为有来源的原文资料；不能凭参考规则补造难度、数值、等级或对手类型，也不能因为原文没有这些目标规则字段就拒绝、重试或编造卡片。来源事实、推断与 GM 建议继续区分。

## 从现有实现核对

以下是本次定位到的检查入口，不是预先断言其中每一项都需要改动：

| 入口 | 需要核对的行为 |
| --- | --- |
| backend/domain/profiles/cthulhu-dark-2e.json | name/summary 的“规则档案”、risk_axes、scene_guidance 与 prompts 是否把洞察、失败代价等参考语义当成实际运行要求 |
| backend/domain/profiles/daggerheart.json | 叙事卡型、环境/对手方法哪些应保留，哪些语句可能隐含系统规则 |
| backend/domain/profiles/module-prep.json | “供目标规则档案重新编排”和 flag_rule_conversion 是否仍影响可达入口；通用板块不得成为必经转换阶段 |
| backend/app/artifacts.py | 多处 TARGET_PROFILE_JSON、planning_profile 和 profile.model_dump 进入真实模型消息；覆盖局部消化、整板规划、正文生成和修复/重试，不只改一个主提示 |
| backend/app/prep.py、backend/app/structure.py | 抽取、章节/剧情线规划是否已经传播目标规则假设，或要求原文未提供的内容 |
| frontend/workbench.js | 中性显示名之外，运行页 profile 指导、风险/GM move 文案是否仍向 GM 宣称必须按参考规则操作 |
| backend/domain/models.py、service.py 及现有契约测试 | 必填字段与验证是否仍要求某目标规则的机制；已有叙事契约和来源引用保持有效 |

先用一张简短的证据表记录“实际可达入口 → 发送内容/验证行为 → 保留或修正 → 理由”，再完成有证据的最小修正。可以直接在本轮交付中完成这一过程，无需为每处文字调整再等待批准。对于未调用的历史入口，记录证据，不展开 R6 退役。

## 实现范围

- 复用当前 profile、消息构造、校验和展示接口；不新建规则转换引擎、第二套板块模型、生成管线或配置平台。无需新增“你运行什么规则”的必答流程。
- 默认保留 cthulhu-dark-2e、daggerheart 等持久化兼容 ID 及现有资料、任务、计划引用。显示文案与提示可以中性化；仅改 ID 或界面名称不足以通过验收。
- 使用明确且必要的消息边界，避免各处反复堆叠同义禁令。若现有共享接口已能表达边界，完善它；不要另造平行抽象。
- 不改准备选择、ScenePlan 成员与 SessionState 的隔离；不预设玩家路线，不缩减项目内批准资料速查，不允许未批准内容进入运行。
- 本轮不做全库重生成、自动迁移、战斗平衡、旧数据修复、R6/R7 大拆分。保留所有既有未提交维护；不提交、推送或发布。

## 验证与交付

1. 使用合成的 COC 风格与 DND 风格原规则资料，检查实际消息构造与校验。参考档案不能把未提供的洞察机制、Daggerheart Tier/Difficulty/Type 等当作必须补齐的运行内容；若发现此前路径已正确，保留并给出证据。
2. 检查叙事信息仍可用：现实恐怖保留可描述现场、人物目标/扮演提示、障碍与后果；奇幻保留情境功能、对手目标、危险前兆、替代解法与来源。允许原文缺失时明确留空或说明缺口，不能用模板补造事实。
3. 原规则数字与能力在已有来源字段中原样可查，不被自动换算、重写为参考规则数值，也不因“通用”被清除。用有来源的数值反例和无来源的目标机制反例验证边界。
4. 聚焦回归覆盖实际被改的生成/修复消息链和验证行为，加入一个能捕获本次修正的反例；不要只断言新名称或提示包含几个词。保留现实恐怖、奇幻、来源、复核及准备选择的受影响回归。
5. 所有写入使用临时合成库；Python 脚本需要外层临时路径保护，避免旧 finally 恢复路径后 init_db 触及正式库。默认不调用真实模型，离线消息检查不能宣称新产物质量已通过。

交回：证据表、实际改动与保留理由、检查命令/结果、兼容影响和剩余限制，更新 audit/backlog 后交 Sol 独立复审。若发现必须新增产品决策的分歧，先留下具体触发和影响；不要重新询问已确认的产品目标，也不要自行扩展为规则适配产品。
