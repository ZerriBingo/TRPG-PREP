# TRPG Prep 第二次方向重评

更新时间：2026-08-26  
状态：**当前有效的产品与开发方向；取代 2026-08-25 文档中的阶段顺序和完成判断。R1 已获 GM 正式生成确认，R2 的边界切分、任务删除和显式提升主链已实现；多来源编辑、聚类与拆分合并仍待完成。**  
触发原因：GM 已确认人工金标准卡片可用，但无法从空白工作台自行生成候选、事实、备团产物或场景包；复核页没有内容，新工作台没有可操作的 LLM 入口，现有交互也没有把跨页章节范围当成第一类输入。

## 1. 结论

项目已不再停留在“完成 P1.3、等待 GM 复核真实候选”。截至 2026-08-26，R1 已把上传、跨页任务、LLM 执行器、候选队列和工作台入口接通；新配置的真实模型已完成单窗生成。当前状态是：

> **一个已证明部分人工卡片有桌边价值，并已建立“上传 PDF -> 跨页范围 -> 真实 LLM 候选 -> 对应复核队列”工程闭环的原型；正式 GM 重试确认、候选提升、备团产物生成和场景包流转仍未完成。**

因此立即暂停规则档案扩展、第二模组扩展和独立复核 UI 优化。恢复功能开发时，第一目标不是新增卡型，而是让 GM 从一个全新数据库出发，完成以下链路：

`选择 PDF 与跨页备团范围 -> 选择目标板块和本次游戏目标 -> 调用 LLM -> 得到带多页证据的候选 -> GM 复核并明确提升为事实 -> 生成备团产物草案 -> GM 确认场景包 -> 桌边运行`

复核队列只是这条链路的中间站，不能继续作为没有上游入口的顶层功能。卡片仍是最终的桌边视图，不是导入和理解模组的起点。

## 3. 问题根因

### 3.1 先建了复核站，没有建候选生产线

新领域管线刻意与旧 LLM 三件套隔离，这是正确的安全边界；但开发顺序把隔离做成了断路。旧 `backend/app/llm.py` 能访问模型，新 `shadow_*` 表能保存候选，工作台也能复核，却没有服务把三者连接起来。

新的管线应复用经过整理的模型网关能力，但不能把旧 `overview/locations/encounters` 输出重新接回工作台。模型响应必须直接进入当前候选契约，并保留任务、范围、模型、prompt/schema 版本和失败记录。

### 3.2 把“处理窗口”误当成“用户的备团范围”

单页预览和精确页码适合证据定位，却不适合作为 GM 选择备团内容的主要方式。背景可能在一页开始、NPC 信息在后续页补全、场景发展与结局也常跨页。单章备团应优先选择连续或少量离散的页段，再由系统切成模型可以处理的窗口。

后续必须同时存在三种不同粒度：

1. **备团范围 `PrepScope`**：GM 选择的章节或多个页段，例如 `159-165, 172, 180-183`。
2. **抽取窗口 `ExtractionWindow`**：系统从范围内生成的重叠多页窗口，用于控制上下文和失败重试；窗口边界不能被当作内容边界。
3. **证据引用 `SourceRef`**：候选最终指向的精确页、摘录或区域；同一事实可以拥有多条引用。

范围不应继续存成最多 100 个展开页码。应增加第一类 `PageSpan {start, end, label?}`，并只在实际读取时展开。

### 3.3 “接受候选”没有产生可使用的事实

当前接受状态只留在影子表中，这避免了模型污染运行包，却没有下一步。新的提升操作必须是单独、明确且可审计的 GM 命令：

`candidate accepted -> promote -> SourceFact(evidence_status = source_fact 或 inference) -> 记录 candidate_id 和 review_id`

接受不等于提升；提升也不等于自动生成卡片。每一次边界变化都需要可见的来源和历史。

### 3.4 卡片视图早于备团任务

GM 的自然目标是“我要用这段模组准备一场约两小时的现实恐怖/奇幻冒险游戏”，而不是先选择事实表或空复核队列。新的首页第一任务应是：

- 选择或导入 PDF；
- 选择章节/页段；
- 选择“现实恐怖”“奇幻冒险”或“通用备团”；
- 写明本次时长、预期起点和已有玩家状态；
- 选择模型并确认开始。

事实网、候选复核、产物卡和运行模式随后按任务状态逐步开放。

## 4. 三板块方向是否改变

三个板块继续保留，卡型判断基本成立；改变的是实现顺序和它们在管线中的位置。

### 4.1 现实恐怖

仍是第一条真实垂直切片。目标不是把 COC 原文逐页改写，而是从跨页章节范围生成：

- GM-only 章节/单元背景；
- 谜团简报和本次游戏起点；
- 调查场景与场景间入口；
- 功能 NPC；
- 线索网与代价式揭示；
- 恐怖威胁、压力/仪式/追击钟；
- 多种收束结果和下一章接口；
- 必要的玩家展示材料。

### 4.2 奇幻冒险

继续以 Daggerheart 的环境、敌人意图、GM 移动、动态后果和回应玩家选择为启发，不复制版式，也不把原模组改成线性剧情脚本。恢复本板块开发前，必须先完成《狂野逐羊》跨页备团闭环；产物仍以冒险框架、场景、环境、意图敌人、阵营响应、倒计时和后果为主。

### 4.3 通用备团

通用备团既是可选用户产物，也是现实恐怖和奇幻冒险转换之前的内部材料层。它负责章节地图、场景抽取、人物功能、威胁逻辑、线索图、时间线和转换问题；它不直接启动桌边规则。

## 5. 新的产品主链路

### Stage A：来源与备团范围

建立源文件版本、PDF 元数据、目录/章节候选和 `PageSpan`。范围输入至少支持：

- 单个连续页段；
- 多个离散页段；
- 章节书签或目录条目；
- 从已保存范围继续增补。

### Stage B：LLM 事实候选

服务端根据范围生成有重叠的多页窗口，调用当前配置的模型，输出严格候选 schema。失败只重试窗口，不丢失已完成结果。新工作台必须提供模型配置、模型列表/连接测试、创建任务、开始/取消/重试和进度状态。

### Stage C：跨页事实复核与提升

复核以备团任务、场景/实体聚类和范围交集为主要组织方式，单页只是证据定位器。GM 可以拆分、合并、编辑、接受、拒绝，并显式把已接受候选提升为事实；多页引用在编辑与刷新后必须完整保留。

### Stage D：备团产物草案

模型只读取已提升事实和目标板块契约，生成字段级带来源的产物草案。现实恐怖优先生成完整单元包，而不是先堆独立卡片数量。产物也要复核，未批准草案不能进入场景包。

### Stage E：场景包与运行

GM 选择已批准产物，系统确定性组装本次游戏场景包；LLM 只提供遗漏提醒或明确标记的 GM 建议。现有运行器、状态恢复和复盘继续作为下游使用。

## 6. 恢复开发后的阶段顺序

### R1：空白数据库到候选队列

实现 `PrepScope/PageSpan/PrepJob`、范围解析、工作台 LLM 设置与连接测试、服务端模型执行器、进度与失败恢复。

验收：删除临时测试数据后，GM 能选择一个真实 PDF，输入 `159-165`，选择现实恐怖和模型，点击一次开始后看到真实候选；不需要手写 API 请求。

### R2：跨页候选到批准事实

完善多来源编辑、跨页预览、实体/场景聚类、拆分/合并和显式提升。

验收：至少一条事实引用两个不同页码；刷新后引用、编辑历史和来源版本不丢失；未提升候选仍不能进入卡片。

### R3：批准事实到现实恐怖单元包

依据人工金标准生成谜团、场景、NPC、线索、威胁、时钟、结局和 GM-only 背景草案，并提供字段级来源复核。

验收：GM 从同一任务生成可编辑单元包，与人工金标准做 diff，并记录准备时间和修改量。

### R4：两小时运行验证

从批准单元包创建一次场景包并真实运行，保存检索、翻页、修改、遗漏和偏航记录。

验收：能够说明 LLM 版本是否比人工整理减少工作；若没有减少，停止扩大自动化并修正产物。

### R5：第二样本与奇幻冒险

先用《无光的灯塔》复验现实恐怖，再用《狂野逐羊》建立奇幻冒险垂直切片。只有两个板块都通过，才考虑奈面章节级扩张和《龙金劫》复杂片段。

## 7. 当前明确暂停

- 不继续扩展 P2 规则 profile。
- 不单独优化一个没有候选上游的复核页。
- 不批量转换奈面 660 页。
- 不扩展旧 `overview/locations/encounters` 三件套。
- 不把模型自由聊天或玩家行动建议接入桌边运行。
- 不以夹具测试通过、候选数量或卡片数量宣称产品完成。

## 8. 冗余与遗留代码策略

本次删除中转用 `run.bat`，由 `start.bat` 直接负责依赖检查和启动；`start.vbs` 仅提供隐藏窗口入口。删除只服务旧启动故障排查、并带硬编码路径的 `scripts/debug_vbs.py`。

旧 `backend/app/analyze.py`、`generate.py`、旧 campaign API 和相应测试暂时保留为兼容/研究代码，但不得继续扩展。R1 完成后再做一次引用审计：若新管线已复用所需的 PDF 摄入和 LLM 适配能力，就把旧管线移入明确的 legacy 区或删除，而不是长期与新产品并列。
