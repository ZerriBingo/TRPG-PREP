# LLM 管线与人工复核方案

目标不是让模型“读懂整本书并写一篇漂亮摘要”，而是让模型在受限范围内减少重复摘录工作，同时保留 GM 对事实、取舍和桌边节奏的最终控制。

当前状态说明（2026-08-26）：旧后端拥有 OpenAI 兼容网关，影子 API 能保存外部提交的候选，但新工作台尚未连接两者。本文件描述目标管线，不代表端到端功能已经可用；恢复开发顺序以 `REASSESSMENT_2026-08-26.md` 为准。

## 1. 权限模型

| 层级 | 允许的自动化 | 是否可直接进入运行包 |
|---|---|---|
| 文件/页元数据 | 文件校验、页码、文本密度、标题候选、图片页提示 | 可以；这是确定性数据 |
| 事实候选 | 从指定页抽取实体、事件、线索、威胁和引文 | 不可以，必须复核 |
| 关系候选 | 合并同名实体、建议线索指向、发现矛盾 | 不可以，必须复核 |
| 板块资产草案 | 依据已批准事实填写卡片字段 | 不可以，必须复核 |
| 场景编排建议 | 从已批准卡片建议节拍、时钟和入口 | 不可以，GM 明确确认后才可运行 |
| 运行时问答 | 只检索已批准资产和源页，回答带引用 | 不写回事实；GM 可手工记录 |

核心原则：**模型输出永远是 candidate；approved 是人的状态，不是模型的自信分数。**

## 2. 推荐管线

### Stage 0：摄入与结构

确定性完成：PDF 哈希、页数、文本/扫描页分类、页图、目录/标题候选、章节范围、源文件版本。GM 通过 `PrepScope.page_spans` 选择一个或多个连续页段，例如 `159-165, 172, 180-183`；LLM 可帮助识别标题层级，但不能改写范围或页码。

### Stage 1：受限事实抽取

系统把备团范围切成有重叠的多页 `ExtractionWindow`，而不是把每一页当成独立内容单元。窗口只用于控制上下文、进度和失败重试；跨窗口的实体和事实必须在后续复核中合并。输出每条候选：

- `claim_id`
- `text`
- `kind`
- `source_refs`（一条或多条精确页码 + 片段/区域）
- `evidence_status = model_candidate`
- `confidence`（仅供排序，不代表批准）
- `possible_links`
- `open_questions`

提示词必须要求模型在原文没有依据时返回空/未确认，而不是补写常识。

### Stage 2：实体与关系复核

先用确定性规则按页、名称和别名聚类，再让模型提出合并/拆分建议。GM 可以接受、拒绝或编辑。矛盾事实并存时保留两个候选并标注冲突，不强行平均成一句话。

### Stage 3：通用备团资产

只从 `approved` 事实生成 `scene_extract`、`character_function`、`threat_logic`、`timeline` 和 `clue_graph`。每个字段保存其支持的事实 ID；无法支持的字段进入 `open_questions`。

### Stage 4：目标规则转换

用 RuleProfile 的卡型定义和 scene guidance 生成目标规则草案。转换提示词必须同时看到：

- 已批准事实；
- 通用资产；
- 目标规则 profile；
- 当前场景目标/页范围；
- 不允许发明内容的约束。

模型不得读取未审核候选来“补足”卡片。

### Stage 5：场景包编排

默认采用确定性组装：GM 选择卡片，系统生成结构化 `ScenePlan` 草案；LLM 只能提出节拍文字建议和遗漏提醒。若建议没有事实来源，必须标为 GM 建议，不能默认为模组内容。

### Stage 6：检索式运行辅助

运行中允许问：

- “这个 NPC 现在想要什么？”
- “本场尚未揭示、且来自当前章节的线索有哪些？”
- “这个时钟推进后应描述什么变化？”

回答只来自已批准包和明确选定的源页，附页码/卡片引用；检索不到时返回缺口，不进行自由创作。即兴创作由 GM 手工写入运行日志，另标 `gm_authored`。

## 3. 复核队列

每个任务应产生可恢复的队列项，而不是一次性覆盖结果：

- `needs_review_fact`
- `needs_review_entity_link`
- `needs_review_conflict`
- `needs_review_card`
- `missing_source`
- `invalid_output`
- `generation_failed`

队列项至少保存：输入页范围、源文件版本、模型、prompt/schema 版本、原始输出、解析错误、重试次数、编辑历史和当前状态。

队列在产品界面中按备团任务、场景/实体聚类和页段交集组织；单页筛选只用于定位证据，不能成为主要工作流。空队列必须提供“创建备团任务”入口，不能只显示无内容状态。

## 4. 失败与恢复

- JSON 截断：保留原始响应，尝试结构修复；失败则只重试该页段。
- API 超时/限流：任务幂等，按 chunk 重试，不重新覆盖已批准结果。
- 来源不足：输出缺口而不是编造；允许 GM 手工补一条带 `gm_authored` 的事实。
- 实体冲突：保留冲突并要求选择；不能用名称相似自动覆盖。
- 模型升级：新旧输出并排 diff，旧的 approved 资产不自动重写。
- 用户中断：任务状态可恢复，已完成 chunk 可继续使用。

## 5. 数据模型增量（先写测试再改代码）

当前领域模型已经有 `SourceFact`、`DerivedCard`、`ScenePlan` 和 `SessionState`，但要支持本方案，后续需要逐步增加：

- `PageSpan`、`PrepScope`、`PrepJob` 和 `ExtractionWindow`
- `SourceRef.excerpt` / `region` / `source_version`
- `EvidenceStatus` 与 `ReviewState`
- `FactCandidate` 或等价的候选/审核记录
- `GenerationRun`：模型、prompt、schema、输入范围、耗时、成本、原始输出摘要
- `ReviewTask`：状态、负责人、编辑差异、拒绝原因
- `ModuleMap` / `ChapterUnit`
- 资产到事实的字段级 provenance，而不仅是整卡 `fact_ids`

不要一次性重写所有模型。先用奈面单章和《无光的灯塔》建立最小夹具，确认字段真的减少 GM 工作后再迁移。

## 6. 质量门槛

每个阶段都应自动检查：

- 关键字段是否有来源或 `gm_authored` 标记；
- 卡片是否引用已批准事实；
- 线索是否有至少一个可达场景或明确“仅作背景”；
- 时钟每阶段是否有可描述变化和触发后果；
- 场景是否有至少两个合理入口/出口，除非原文明确是封闭场景；
- GM-only 内容是否误入 handout/player_safe；
- 运行计划是否引用了正确 profile 和已选卡片。

## 7. 何时允许扩大自动化

必须先完成三个对照：

1. 奈面“咀咀屋”人工金标准 vs 同范围 LLM 候选。
2. 《无光的灯塔》人工金标准 vs 候选，检验调查/恐怖而非战斗卡。
3. 《狂野逐羊》人工金标准 vs 候选，检验环境/敌人意图/倒计时。

若模型在其中任何一类反复丢失来源、把推断写成事实、把失败写成挡板或把场景线性化，就只改善提示和审核工具，不扩大页数或规则档案。

在开始上述三个内容对照前，必须先通过更基础的产品门槛：从空白数据库选择真实 PDF 和跨页范围，工作台能够调用模型、显示候选、提升批准事实并生成至少一种备团产物草案。夹具直接向 API 提交 `raw_response` 不算通过。
