# LLM 管线与人工复核方案

目标不是让模型“读懂整本书并写一篇漂亮摘要”，而是让模型在受限范围内减少重复摘录工作，同时保留 GM 对事实、取舍和桌边节奏的最终控制。

当前状态说明（2026-09-03）：新备团任务已经接入 semantic-v2 管线。语义段负责逻辑归属，传输窗口只负责控制模型请求大小；窗口观察先保存在内部任务中，段级归并完成后才公开复核候选。具体的传输或恢复策略可以调整，但必须保持来源覆盖、逻辑归属和可恢复性。

规则边界更正（2026-10-31）：使用目标与规则边界以 `PRODUCT_GUARDRAILS.md` 同日确认内容为准。下文 Stage 3/4 保留旧管线方案用于追溯，其中“通用资产 -> 目标规则转换”的串行设计已被独立板块契约替代，不再作为新实现要求；Cthulhu Dark、Daggerheart 是设计参考，实际运行规则由 GM 决定。各板块产物要求见 `ARTIFACT_CONTRACTS.md`；本次文档更正不表示现有管线已完成实现审查。

## 0. 模型调用边界（2026-11-01）

应用只发 OpenAI-compatible Chat Completions 请求，并通过 `/models` 读取模型列表。`base_url` 归一化只负责定位这两个端点；应用没有 Responses API，也不在 Chat Completions 与 Responses 之间协商或转换。某个本地代理同时提供其他协议，不构成应用复制其多协议适配的理由。

`reasoning_effort` 是可选请求提示，不是模型能力协商或输出保证。用户显式配置后，任务内的重试保持该值不变。运行板块的局部整理另有一个有界恢复：如果用户没有配置档位、上游以 `finish_reason=length` 返回空正文或截断 JSON，应用最多追加一次 `low` 请求；该动作计入同一生成步骤的请求预算并写入诊断，调用结束后不改写保存的配置。其他阶段不自动添加档位。只有调用方明确给出更大的 `escalate_max_tokens` 时，空 `finish_reason=length` 才允许一次预算扩容。上游不支持该参数时，其 HTTP 错误会原样进入任务失败诊断。

响应诊断只保留 usage 数值、结束原因、正文/`reasoning_content` 长度、refusal 是否存在和工具调用数量；不保存 `reasoning_content` 文本。供应商没有报告的 reasoning token 数量保持未知。

## 0b. 身份重整与来源忠实度（2026-11-02）

产物生成在合并决定卡数之前先做一次身份重整。候选不再只来自“跨章节共享剧情线或运行组”：同一备团范围、同一卡型、且引用至少一条共同事实的两张地点/NPC/威胁卡也进入候选。共同事实只是候选信号，判定由重整步骤读取候选的事实闭包后作出；两张异名同实体合并，两个不同人物/地点/威胁即使共用同一条来源也保持分开，一张 NPC 卡只承载一位可扮演人物。重整请求按卡型分块，受现有单块字符与卡数上限约束，超限候选会被报告为未重整而不是截断或吞掉；事实文本进入请求与步骤身份，事实改写会失效对应判定。

素材化提示区分“必填非空”和“有来源支持”：来源未说明时可以在字段内直说缺口，不需要编造工作假设；工作假设只描述这份材料开始时的状态，不得补出动机、交换条件、访问规则或接待流程。来源使用的限定语（看起来、据报道、可能）必须原样保留，不得改写成断言，也不得补出限定语留空的具体细节。

## 1. 权限模型

| 层级 | 允许的自动化 | 是否可直接进入运行包 |
|---|---|---|
| 文件/页元数据 | 文件校验、页码、文本密度、标题候选、图片页提示 | 可以；这是确定性数据 |
| 事实候选 | 从指定页抽取实体、事件、线索、威胁和引文 | 不可以，必须复核 |
| 关系候选 | 合并同名实体、建议线索指向、发现矛盾 | 不可以，必须复核 |
| 板块资产草案 | 依据已批准事实填写卡片字段 | 不可以，必须复核 |
| 场景编排建议 | 从已批准卡片建议节拍、时钟和入口 | 不可以，GM 明确确认后才可运行 |
| 运行时问答 | 只检索已批准资产和源页，回答带引用 | 不写回事实；GM 可手工记录 |

核心原则：**模型输出永远是 candidate；approved 是人的状态，不是模型的自信分数。**

## 2. 推荐管线

### Stage 0：摄入与结构

确定性完成：PDF 哈希、页数、文本/扫描页分类、页图、目录/标题候选、章节范围、源文件版本。GM 通过 `PrepScope.page_spans` 选择一个或多个连续页段，例如 `159-165, 172, 180-183`；LLM 可帮助识别标题层级，但不能改写范围或页码。

### Stage 1：受限事实抽取

新任务先让 LLM 对选定页生成不重叠的语义段分区。语义段是逻辑完整性的单位；页边界或字符预算不能单独证明地点、人物、事件已经结束。

随后系统为每个语义段建立一个或多个 `ExtractionWindow`。窗口是传输和恢复单位，不是事实单位：它可以读取相邻上下文；当语义段超过传输预算时，可以继续拆成连续页范围或连续字符范围。字符范围必须无损覆盖原文，不能用截断来制造新的语义段。

窗口抽取产生的 `window_observation` 候选保存在内部任务中，不直接进入 GM 复核队列。输出每条候选：

- `claim_id`
- `text`
- `kind`
- `source_refs`（一条或多条精确页码 + 片段/区域）
- `evidence_status = model_candidate`
- `confidence`（仅供排序，不代表批准）
- `possible_links`
- `open_questions`

提示词必须要求模型在原文没有依据时返回空/未确认，而不是补写常识。

语义规划不可用或返回无效分区时，任务可以采用持久化的无损传输策略继续处理。该策略保证选定页和字符范围完整传输，但不把请求切点冒充为语义边界。

### Stage 1.5：语义段归并与公开

当一个语义段的所有传输窗口都成功后，系统收集该段的窗口观察，按候选 ID 去重并保留所有支持性 `source_refs`。归并模型只合并有来源支持的同一主张，不能因为窗口相邻就把不同事实平均成一句话。

如果观察内容超过归并输入预算，系统按候选完整记录分批处理，再对批次结果进行分层归并。中间归并任务始终保持内部可见；每个语义段只有最终归并任务可以成为公开复核入口。归并结果为空时使用不丢失证据的确定性重复主张合并。若模型已经分别验证了各批候选、候选仍彼此不同、且完整结果没有超过公开候选上限，系统可以通过父任务 ID 与候选签名创建一个确定性的无损最终归并结果；它不再次请求模型，仍执行同一套严格来源校验。结果超过公开上限或无法通过校验时，任务失败并保持队列为空，绝不以截断候选换取完成状态。

只有所有语义段都完成最终归并后，`segment_result` 才进入复核队列。任一窗口或语义段归并失败，其他段的部分结果也不会提前公开。

### Stage 2：实体与关系复核

先用确定性规则按页、名称和别名聚类，再让模型提出合并/拆分建议。GM 可以接受、拒绝或编辑。矛盾事实并存时保留两个候选并标注冲突，不强行平均成一句话。

### Stage 3：通用备团资产（历史串行方案，已替代）

只从 `approved` 事实生成 `scene_extract`、`character_function`、`threat_logic`、`timeline` 和 `clue_graph`。每个字段保存其支持的事实 ID；无法支持的字段进入 `open_questions`。

### Stage 4：目标规则转换（历史串行方案，已替代）

用 RuleProfile 的卡型定义和 scene guidance 生成目标规则草案。转换提示词必须同时看到：

- 已批准事实；
- 通用资产；
- 目标规则 profile；
- 当前场景目标/页范围；
- 不允许发明内容的约束。

模型不得读取未审核候选来“补足”卡片。

### Stage 5：场景包编排

默认采用确定性组装：GM 选择卡片，系统生成结构化 `ScenePlan` 草案；LLM 只能提出节拍文字建议和遗漏提醒。若建议没有事实来源，必须标为 GM 建议，不能默认为模组内容。

### Stage 6：检索式运行辅助

运行中允许问：

- “这个 NPC 现在想要什么？”
- “本场尚未揭示、且来自当前章节的线索有哪些？”
- “这个时钟推进后应描述什么变化？”

回答只来自已批准包和明确选定的源页，附页码/卡片引用；检索不到时返回缺口，不进行自由创作。即兴创作由 GM 手工写入运行日志，另标 `gm_authored`。

## 3. 复核队列

每个任务应产生可恢复的队列项，而不是一次性覆盖结果：

- `needs_review_fact`
- `needs_review_entity_link`
- `needs_review_conflict`
- `needs_review_card`
- `missing_source`
- `invalid_output`
- `generation_failed`

队列项至少保存：输入页范围、源文件版本、模型、prompt/schema 版本、原始输出、解析错误、重试次数、编辑历史和当前状态。

复核记录应围绕备团任务和 GM 的当前决策组织；具体的分组、分页、筛选和入口布局由实际工作流决定。空状态应能引导用户回到有意义的下一步。

对于 semantic-v2 任务，复核入口按备团任务和语义段结果显示，而不是按每个传输窗口重复显示。内部窗口观察和中间归并任务仍保留用于恢复、审计和诊断，但不构成用户可操作的复核候选。

## 4. 失败与恢复

- JSON 截断：保留原始响应，尝试结构修复；失败则只重试该页段。
- API 超时/限流：任务幂等，按 chunk 重试，不重新覆盖已批准结果。
- 语义规划失败：使用无损的备用传输策略，明确标记为兜底，不把请求切点当成语义事实。
- 归并输入过大：按完整候选记录分批并进行有限轮次的分层归并；不以 `[:N]` 静默丢弃候选。
- 归并失败或无法收敛：保留内部任务和错误，重试时使用新的模型快照；在完整成功前不公开部分结果。
- 来源不足：输出缺口而不是编造；允许 GM 手工补一条带 `gm_authored` 的事实。
- 实体冲突：保留冲突并要求选择；不能用名称相似自动覆盖。
- 模型升级：新旧输出并排 diff，旧的 approved 资产不自动重写。
- 用户中断：任务状态可恢复，已完成 chunk 可继续使用。

## 5. 数据模型增量（先写测试再改代码）

当前领域模型已经有 `SourceFact`、`DerivedCard`、`ScenePlan`、`SessionState`、`PrepJob`、`ExtractionWindow` 和影子任务/候选记录。后续仍按增量方式完善：

- `PageSpan`、`PrepScope`、`PrepJob` 和 `ExtractionWindow`
- `SourceRef.excerpt` / `region` / `source_version`
- `EvidenceStatus` 与 `ReviewState`
- `FactCandidate` 或等价的候选/审核记录
- `GenerationRun`：模型、prompt、schema、输入范围、耗时、成本、原始输出摘要
- `ReviewTask`：状态、负责人、编辑差异、拒绝原因
- `ModuleMap` / `ChapterUnit`
- 资产到事实的字段级 provenance，而不仅是整卡 `fact_ids`

模型和数据结构按增量方式演进，在稳定接口处用小型真实夹具确认字段确实减少 GM 工作后再扩大范围。

## 6. 质量门槛

每个阶段都应自动检查：

- 关键字段是否有来源或 `gm_authored` 标记；
- 卡片是否引用已批准事实；
- 线索是否有至少一个可达场景或明确“仅作背景”；
- 时钟每阶段是否有可描述变化和触发后果；
- 场景是否有至少两个合理入口/出口，除非原文明确是封闭场景；
- GM-only 内容是否误入 handout/player_safe；
- 运行计划是否引用了正确 profile 和已选卡片。

## 7. 何时允许扩大自动化

必须先完成三个对照：

1. 奈面“咀咀屋”人工金标准 vs 同范围 LLM 候选。
2. 《无光的灯塔》人工金标准 vs 候选，检验调查/恐怖而非战斗卡。
3. 《狂野逐羊》人工金标准 vs 候选，检验环境/敌人意图/倒计时。

若模型在其中任何一类反复丢失来源、把推断写成事实、把失败写成挡板或把场景线性化，就只改善提示和审核工具，不扩大页数或规则档案。

在开始上述三个内容对照前，必须先通过更基础的产品门槛：从空白数据库选择真实 PDF 和跨页范围，工作台能够调用模型、显示候选、提升批准事实并生成至少一种备团产物草案。夹具直接向 API 提交 `raw_response` 不算通过。
